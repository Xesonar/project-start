# Проверка решения «Старт»

## Назначение и приоритетный сегмент

«Старт» помогает студентам 1–2 курса IT- и дизайн-направлений, у которых
ещё нет проектного опыта, выбрать посильный внеучебный проект, понять пробелы
в навыках и отправить первый отклик на конкретную роль.

Проблема MVP сформулирована как гипотеза: студент хочет получить первый
проектный опыт, но информация разрознена, требования трудно сопоставить со
своими навыками, а результат участия негде подтвердить. До пилота эта гипотеза
не считается доказанным фактом и должна быть проверена интервью и метриками.

## Основной сценарий проверки

1. Открыть Mini App из тестового бота MAX. Для локальной проверки опубликовать frontend через HTTPS-туннель и указать этот адрес в настройках бота.
2. На главной проверить персональный порядок проектов и объяснение рекомендации.
3. Открыть проект, проверить процент совпадения и список недостающих навыков.
4. Выбрать ещё не использованную роль и отправить отклик.
5. Открыть «Отклики» и убедиться, что заявка имеет статус «На рассмотрении».
6. Проверить отмену ожидающего отклика и повторный отклик на ту же роль.
7. Открыть `/admin`, войти с паролем `ADMIN_PASSWORD`, указать MAX-чат проекта,
   отправить студенту сообщение и принять заявку.
8. Проверить у студента экран «Команда», кнопку входа в чат проекта, описать
   личный вклад, приложить ссылку на результат и отправить работу на проверку.
9. В админке вернуть работу на доработку с комментарием; у студента исправить
   описание и отправить повторно, затем подтвердить результат в админке.
10. Заполнить общий результат проекта и нажать «Завершить и подтвердить участников».
    До подтверждения работы каждого участника кнопка завершения недоступна.
11. Открыть «Портфолио», создать публичную ссылку и проверить её без авторизации.

Ожидаемый результат: студент проходит путь от подбора проекта до публичного
подтверждённого результата; произвольный пользователь не может попасть в
портфолио проекта без принятия в его команду.

## Тестовые роли и данные

- Студент: реальный пользователь MAX, вход по подписанному `initData`.
- Организатор: `/admin`, пароль берётся из `ADMIN_PASSWORD` окружения.
- Все проекты и организации из seed — тестовые данные для проверки MVP, а не
  реальные предложения организаций.
- Seed идемпотентен и автоматически запускается после миграций при старте backend.

## Данные и интеграции

- PostgreSQL хранит профиль, навыки, заявки, команды, сдачи работ, решения
  организатора и подтверждения участия.
- MAX Bridge передаёт подписанный `initData`; подпись и срок действия проверяются backend.
- MAX Bot API используется для чат-меню и уведомлений после регистрации webhook.
- DeepSeek API опционален: формирует короткие объяснения для детерминированного
  top-5, но не меняет порядок. При ошибке подбор продолжает работать без текста AI.
- Контакты, университет и цель студента не попадают в публичное портфолио.

## Известные ограничения MVP

- Каталог наполнен синтетическими seed-данными; импорта из систем вузов пока нет.
- Организации пока создаются seed-скриптом; проекты можно добавлять через админку.
- Студент может состоять максимум в трёх активных командах; `/me/teams` показывает
  все активные команды и историю завершённых проектов.
- В админке есть базовая воронка пилота; расширенные срезы по факультетам пока не реализованы.
- Реальный MAX-сценарий требует HTTPS, ссылки Mini App у бота и зарегистрированного webhook.
- LLM не является источником официальных данных и работает только с переданными
  кандидатом-проектом и профилем.

## Пилот и измеримый эффект

Первый пилот: одна проектная площадка российского университета, 100 студентов
1–2 курса и 10 организаторов, продолжительность 4 недели. Доступ — через QR-код
и бота MAX в объявлениях проектного офиса и учебных чатах.

Гипотезы успеха пилота:

- не менее 60% начавших завершают профиль;
- не менее 35% завершивших профиль отправляют первый отклик в течение 7 дней;
- медианное время от входа до первого отклика — не более 5 минут;
- не менее 80% заявок получают решение организатора за 48 часов;
- не менее 20 подтверждённых результатов появляется в портфолио за пилот.

После пилота: интервью с участниками и организаторами, проверка причин отказа,
затем подключение второго факультета. Целевые значения являются гипотезами,
а не уже достигнутыми показателями.

## Масштабирование

Неизменное ядро: профиль навыков, скоринг, роли, заявка, команда и подтверждение
результата. Переменная часть: справочники специальностей, правила конкретного
вуза, источники проектов, роли организаторов, политика хранения данных и SSO.

Порядок тиражирования: факультет → университет → несколько партнёрских вузов
одного региона → межвузовский каталог. Для каждого нового контекста нужны
владелец процесса, модератор организаций, импорт проектов и соглашение о данных.

## Риски

- Фальшивые проекты: допуск организаций и аудит действий организатора.
- Ошибочный подбор: объяснимый скоринг и возможность пользоваться каталогом без AI.
- Персональные данные: минимизация полей, ограничение публичной выдачи, удаление
  профиля и регламент хранения перед реальным пилотом.
- Низкая скорость ответа организаторов: SLA пилота и напоминания в MAX.
- Недоступность внешнего AI: детерминированный fallback без блокировки сценария.

## Запуск, остановка и повторный старт

```bash
cp .env.example .env
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml ps

docker compose -f docker-compose.prod.yml stop
docker compose -f docker-compose.prod.yml start

docker compose -f docker-compose.prod.yml down
```

Обычный `down` сохраняет PostgreSQL volume. Команду `down -v` использовать
только для намеренного полного удаления локальных данных.
